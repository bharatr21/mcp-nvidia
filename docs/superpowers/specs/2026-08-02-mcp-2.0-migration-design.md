# MCP 2.0 / 2026-07-28 Spec Migration — Design

- **Date:** 2026-08-02
- **Status:** Approved (pending user review of this document)
- **Target release:** `mcp-nvidia` 1.0.0
- **Branch:** `mcp2`

## 1. Context

The MCP `2026-07-28` specification shipped on 2026-07-28 alongside `mcp` Python SDK `2.0.0`. It is a breaking overhaul of the protocol, not an incremental revision. Three changes dominate the impact on this repository:

1. **Stateless core.** The `initialize` / `notifications/initialized` handshake and the `Mcp-Session-Id` header are removed. Protocol version and client capabilities now travel in `_meta` on every request.
2. **HTTP+SSE transport is formally Deprecated** under the new feature lifecycle policy. The entire current `http_server.py` transport layer is built on it.
3. **The Python SDK v1 → v2 migration is its own breaking change**, independent of the spec: the decorator handler API is gone.

Separately, the spec now standardises interactive UI through the **MCP Apps extension** (`io.modelcontextprotocol/ui`), which supersedes the third-party `mcp-ui-server` package this project currently depends on.

This document covers both, shipped together as one breaking `1.0.0` release.

## 2. Goals and non-goals

### Goals

- `mcp-nvidia` speaks the `2026-07-28` protocol correctly and completely.
- Remote deployment serves Streamable HTTP; the deprecated SSE transport is retired.
- Existing users on older clients are protected by a pinned `0.9.0` release.
- `mcp-ui-server` is replaced by the standard MCP Apps extension.

### Backward compatibility: preserve by default, break for simplicity

1.0.0 is already a breaking release, so the question is never "may we break compatibility" but "does *this* break buy enough simplicity to be worth it". The rule for every decision in this document and the work that follows from it:

- **Preserve compatibility when it is cheap.** Serving both protocol eras from one `/mcp` endpoint stays, because the SDK's dual-era dispatcher provides it with zero shim code (§3.5). Free compatibility is kept.
- **Break it when preserving it would mean a shim, a compatibility branch, a second code path, or a dependency we would otherwise drop.** A simpler server is worth more than an unused compatibility guarantee.
- **Never break silently.** Anything dropped is named in the 1.0.0 CHANGELOG entry and the README upgrade notice, with the replacement spelled out.

Applied to the decisions below: retiring `/sse` (Decision 1) and dropping `mcp-ui-server` (Decision 6) are breaks that remove whole code paths, so they stand. Dual-era protocol support (Decision 5) is preserved because it costs nothing.

### Non-goals

- Migrating to the high-level `MCPServer` API (see §4, Decision 2).
- Supporting `mcp` 1.x and 2.x simultaneously in one codebase.
- Adopting Roots, Sampling, Logging, Tasks, or subscriptions — none are used today and the first three are now deprecated.

## 3. Verified API surface

Everything in this section was confirmed empirically against `mcp==2.0.0` installed in the `mcp2/` spike venv (Python 3.12), not read from documentation, and **re-verified against `mcp==2.2.0` on 2026-09-10** (the SDK shipped 2.0.1, 2.1.0, 2.1.1 and 2.2.0 after the spike). The low-level `Server` surface is unchanged between the two; the differences are called out inline. **Several published migration-guide claims proved wrong and are corrected here.** This section is the ground truth for the implementation plan.

### 3.1 Low-level `Server`

Handlers are constructor keyword arguments, and take **two** parameters — a `ServerRequestContext` and a typed params object:

```python
Server(
    name: str, *,
    version: str = "", title: str | None = None, ...,
    cache_hints: Mapping[CacheableMethod, CacheHint] | None = None,
    on_list_tools:     (ctx, PaginatedRequestParams | None) -> ListToolsResult
    on_call_tool:      (ctx, CallToolRequestParams)         -> CallToolResult | InputRequiredResult
    on_list_resources: (ctx, PaginatedRequestParams | None) -> ListResourcesResult
    on_read_resource:  (ctx, ReadResourceRequestParams)     -> ReadResourceResult | InputRequiredResult
    ...
)
```

Confirmed instance/class members: `add_request_handler`, `add_notification_handler`, `get_request_handler`, `create_initialization_options`, `get_capabilities`, `run`, `server_info`, `session_manager`, `streamable_http_app`, and an `extensions` dict (instance attribute, initialised to `{}`).

### 3.2 Corrections to widely-published guidance

| Claim (from migration guide / prior analysis) | Verified reality |
| --- | --- |
| `create_initialization_options()` is removed | **Still exists**, and is still *required* — `Server.run()` takes `initialization_options` as a positional argument to serve the legacy handshake era |
| `resultType` must be set on every result | **Not needed** — `result_type` defaults to `"complete"` |
| `ttlMs`/`cacheScope` are set per result | Set once via the **`cache_hints=` constructor param** |
| `streamable_http_app()` is only on `MCPServer` | **Exists on low-level `Server`**, default path `/mcp` |
| `SseServerTransport` is gone | **Still ships** in `mcp.server.sse` |

### 3.3 Result models (all snake_case in Python)

| Model | Fields relevant to us | Defaults |
| --- | --- | --- |
| `ListToolsResult` | `tools`, `ttl_ms`, `cache_scope`, `result_type`, `next_cursor`, `meta` | `ttl_ms=0`, `cache_scope="private"`, `result_type="complete"` |
| `ListResourcesResult` | `resources`, `ttl_ms`, `cache_scope`, `result_type`, … | same |
| `ReadResourceResult` | `contents`, `ttl_ms`, `cache_scope`, `result_type`, `meta` | same |
| `CallToolResult` | `content`, `structured_content`, `is_error`, `result_type`, `meta` | `is_error=False`, `result_type="complete"` |

**`CallToolResult` has no cache fields** (`tools/call` is not cacheable), and its Python field names are now snake_case: `structuredContent` → `structured_content`, `isError` → `is_error`.

**Correction (verified 2026-09-10):** this is *not* a break. Every model keeps its camelCase alias and accepts it as a constructor keyword, confirmed on 2.2.0 for `Tool(**{"inputSchema": …})`, `Resource(mimeType=…)`, `TextResourceContents(mimeType=…)` and `CallToolResult(structuredContent=…, isError=…)`. So `response_builders.py` and the `Tool(**schema)` / `Resource(…)` call sites compile unchanged, and `_get_tool_schemas()` keeps its `"inputSchema"` keys for the SDK generator. Renaming to snake_case in our own code is optional tidying; reading a field back off a result object does require the snake_case name.

### 3.4 Caching

```python
CacheHint(ttl_ms: int = 0, scope: Literal["public","private"] = "private")
CacheableMethod = Literal["prompts/list", "resources/list", "resources/read",
                          "resources/templates/list", "server/discover", "tools/list"]
```

The `"private"` default is wrong for this server's static listings, so `cache_hints` must be set explicitly.

### 3.5 Transport

`Server.streamable_http_app()` returns a `Starlette` app:

```python
streamable_http_app(*, streamable_http_path="/mcp", json_response=False,
    stateless_http=False, event_store=None, retry_interval=None,
    max_request_body_size=4194304,
    session_idle_timeout=1800, max_sessions=10000,        # new in 2.2.0
    transport_security=None, host="127.0.0.1", auth=None,
    token_verifier=None, auth_server_provider=None,
    custom_starlette_routes: list[Route] | None = None, debug=False) -> Starlette
```

Dual-era support is built in and confirmed (constants live in `mcp.server.runner`):

- `HANDSHAKE_PROTOCOL_VERSIONS = ("2024-11-05", "2025-03-26", "2025-06-18", "2025-11-25")`
- `MODERN_PROTOCOL_VERSIONS = ("2026-07-28",)`
- dispatched by `mcp.server.runner.serve_dual_era_loop`

One endpoint therefore serves both old and new clients with **zero shim code**.

Also handled by the SDK, so no project code is needed:

- **Request-header validation.** `mcp.shared.inbound` checks `MCP-Protocol-Version`, `Mcp-Method` and (for `tools/call`, `resources/read`, `prompts/get`) `Mcp-Name` against the body. It rejects a mismatch with HTTP 400 and `HEADER_MISMATCH = -32020`, which the spec renumbered from the draft's `-32001`.
- **`server/discover`**, now a spec MUST, is registered by default on the low-level `Server`.
- **Legacy-era sessions** (≤ `2025-11-25` clients still get `Mcp-Session-Id`) expire after 30 minutes idle and are capped at 10,000 concurrent. These are the 2.2.0 defaults.

**`host` is a security setting, not a bind address.** When `transport_security is None` and `host` is a loopback address (the default `"127.0.0.1"`), the SDK turns on DNS-rebinding protection with `allowed_hosts=["127.0.0.1:*", "localhost:*", "[::1]:*"]`. Behind Railway, every request carries the public `Host` header and would be **rejected** under the default. See Stage 2.

### 3.6 MCP Apps extension

```python
EXTENSION_ID  = "io.modelcontextprotocol/ui"
APP_MIME_TYPE = "text/html;profile=mcp-app"
```

Critically, `Apps` is **purely declarative and additive**:

- `Apps.methods()` returns `()` — no new request handlers to register.
- `Apps` does **not** override `intercept_tool_call` — no `tools/call` interceptor needed, so `compose_tool_call_handler` is not required.

That is what makes MCP Apps viable on the low-level `Server` without migrating to `MCPServer` (whose `extensions=` constructor param is otherwise the only official attachment point).

```python
Apps.add_html_resource(uri, html, *, name=None, title=None, description=None,
    csp: ResourceCsp | None = None, permissions: ResourcePermissions | None = None,
    domain=None, prefers_border=None) -> None

ResourceCsp(connect_domains, resource_domains, frame_domains, base_uri_domains)
```

`Apps` is importable from `mcp.server.apps`. `apps.resources()` returns `ResourceBinding` objects wrapping a `TextResource` with `mime_type="text/html;profile=mcp-app"`. `meta` is `None` unless `csp`/`permissions`/`domain`/`prefers_border` is passed, and then becomes e.g. `{"ui": {"csp": {"connectDomains": [...]}}}`. `apps.settings()` returns `{}`. That is still enough: `get_capabilities()` defaults its `extensions` to `self.extensions`, so the identifier is advertised with empty settings. Tool→app binding is a `_meta` stamp of `{"ui": {"resourceUri": "ui://…"}}` — the `@apps.tool()` decorator does nothing more than this, so it is trivially replicated by hand on our existing tool schemas. Use the nested form only. The MCP Apps spec (`2026-01-26`, still the latest stable) deprecates the flat `_meta["ui/resourceUri"]` key. The optional `_meta.ui.visibility` (`["model", "app"]`) defaults to both, which is what we want. With no `ui.csp`, hosts apply `connect-src 'none'` and allow inline script and style, which the self-contained shell relies on.

### 3.7 Dependency shifts

Resolved by `mcp==2.2.0` (the spike's `2.0.0` resolution is in parentheses):

- `starlette` **0.37 → 1.6.0** (1.3.1) — a major bump that the current `starlette>=0.37.0` pin does not anticipate. The SDK itself only requires `starlette>=0.27`.
- new transitive packages `mcp-types==2.2.0` (lock-stepped with `mcp`) and `httpx2` (replaces `httpx` + `httpx-sse` since 2.0.0b2)
- `pydantic` 2.13.5 (2.13.4), `sse-starlette` 3.4.11 (3.4.6), `uvicorn` 0.52.4 (0.52.1)
- `Requires-Python: >=3.10`, which matches our floor

### 3.8 SDK changes after 2.0.0 that matter here

- **2.1.0:** HTTP notifications on the `2026-07-28` era are acknowledged with `202`, and pre-2026 sessions ignore cache-hint fields. Both were wrong in 2.0.0, and our dual-era tests would have hit them.
- **2.1.0:** handler exceptions are logged at ERROR and clients get a generic message (see Stage 3). `ToolError`/`ResourceError` exist for model-facing messages, but only on `MCPServer`. On the low-level `Server` the equivalent is raising `MCPError`.
- **2.2.0:** idle-session expiry and a session cap for legacy-era Streamable HTTP (§3.5).
- **2.0.1 / 2.1.1:** an import warning for the removed `mcp.server.fastmcp`. Not used by this project.

## 4. Decisions

| # | Decision | Rationale |
| --- | --- | --- |
| 1 | **Retire `/sse`; serve `/mcp` only.** `/sse` and `/sse/messages` return `410 Gone` with a JSON body carrying `moved_to: "/mcp"`. | One live transport path. 410 (not 404) is semantically correct — the endpoint existed and was intentionally removed — and the `moved_to` pointer turns an opaque client hang into a diagnosable error. |
| 2 | **Stay on the low-level `Server`.** | Keeps `_get_tool_schemas()` as the single source of truth feeding both `tools/list` and the SDK generator, so `sdk_generator/` is untouched. §3.6 confirms MCP Apps does not force `MCPServer`. |
| 3 | **Version 1.0.0, requiring `mcp>=2.2.0,<3`**, preceded by a **0.9.0** release pinning `mcp>=1.28,<2.0.0`. | Honest semver for a breaking change. 0.9.0 protects anyone who ran an unpinned `pip install mcp-nvidia` from a transitive SDK upgrade — verified, not hypothetical: the old `mcp>=1.1.0` resolves to `mcp` 2.2.0 today. |
| 4 | **Port integration tests and add conformance tests.** | A mechanical port silently drops exactly the things the new spec requires; those get explicit tests. |
| 5 | **Serve both protocol revisions from `/mcp`** ("C-narrow"). | Free per §3.5 — the work is verifying and documenting it, not building it. |
| 6 | **Replace `mcp-ui-server` with the MCP Apps extension**, rendering **client-side from `structured_content`** (Option 2). | `mcp-ui-server` is a third-party shim for what the spec now standardises. Client-side rendering is the intended MCP Apps model, needs no network round-trip, and works in a locked-down sandbox. |

### 4.1 Rejected alternatives

- **Dual SDK-major support (v1 + v2 shim).** Doubles every handler permanently; the 0.9.0 pin solves the same user problem for far less.
- **Keeping `/sse` live alongside `/mcp`.** Viable — `SseServerTransport` still ships — but rejected in favour of a single transport path.
- **Migrating to `MCPServer`.** Would delete ~280 lines of hand-written JSON Schema, but the SDK generator consumes those schemas, so they would have to be reflected back out of the tool registry. Deferred as a possible separate project.
- **MCP Apps via server-side HTMX endpoints (Option 1).** Smaller diff and reuses the existing `/ui/*` endpoints, but keeps the UI dependent on network access to our server and is not the model MCP Apps is designed around.

## 5. Implementation stages

### Stage 0 — Spike ✅ complete

Findings recorded in §3. Venv at `mcp2/` (added to `.gitignore`). No production code.

### Stage 1 — Core server

Changes to `src/mcp_nvidia/server.py`:

- Convert four decorators to constructor kwargs; each handler gains the `(ctx, params)` signature. Bodies are otherwise unchanged.
- Wrap bare returns: `list[Tool]` → `ListToolsResult`, `list[Resource]` → `ListResourcesResult`, `str` → `ReadResourceResult` with `TextResourceContents`.
- Add `cache_hints` at construction (see below).
- **Keep** the `create_initialization_options()` call at `server.py:673`. `Server.run(read, write, initialization_options, ...)` still takes it as a *required* positional argument, because `run()` wraps `serve_dual_era_loop` and serves the legacy handshake era on stdio as well as the modern era — the client's first request decides which. Removing it would break stdio clients on `2025-11-25` and earlier. Signal handling and graceful shutdown are retained unchanged; `run()` needs no other edits.
- Stamp `_meta={"ui": {"resourceUri": …}}` onto the two tool schemas (see Stage 4).

The cache hints:

```python
cache_hints={
    "tools/list":     CacheHint(ttl_ms=3_600_000, scope="public"),
    "resources/list": CacheHint(ttl_ms=3_600_000, scope="public"),
    "resources/read": CacheHint(ttl_ms=3_600_000, scope="public"),
}
```

A one-hour TTL and `public` scope are correct because tools and SDK resources are generated once at module load and are byte-identical for every caller — there is no per-user data in any of them. Search *results* are never cached; only listings are.

Changes to `src/mcp_nvidia/lib/response_builders.py`:

- `build_tool_result`: rename `structuredContent` → `structured_content`, `isError` → `is_error`. No `result_type` needed.
- `build_tool_result_with_ui`: drop the `mcp_ui_server` import (Stage 4).

`_get_tool_schemas()`, `_get_tool_definitions()`, `_generate_sdk_files()` and the whole of `sdk_generator/` are **not modified**.

### Stage 2 — Transport

`src/mcp_nvidia/http_server.py` is rewritten around `streamable_http_app()`:

| Route | Behaviour |
| --- | --- |
| `/mcp` | Streamable HTTP; serves both protocol eras |
| `/sse`, `/sse/messages` | `410 Gone`, JSON `{error, moved_to: "/mcp"}` |
| `/health` | `transport: "streamable-http"`, `endpoints.mcp: "/mcp"` |
| `/` | health (unchanged) |
| `/ui/filter`, `/ui/content`, `/ui/citation/{index}` | **Removed** — see below |

`SseServerTransport` and `sse.connect_sse` are deleted. The `/ui/*` HTMX endpoints have no consumer under Decision 6 (client-side rendering) and are removed rather than left as dead routes; this is reversible if a standalone browser demo is wanted later.

The host Starlette app's `lifespan` **must** enter `mcp.session_manager` — mounted sub-apps never run their own lifespan, and getting this wrong fails silently at request time rather than at boot. This gets a dedicated test.

**Transport security must be set explicitly.** `run_http_server()` binds uvicorn to `0.0.0.0`, but that value does not reach `streamable_http_app(host=...)`. Left at its default, the SDK enables localhost-only DNS-rebinding protection and rejects Railway traffic (§3.5). Pass an explicit `TransportSecuritySettings` whose `allowed_hosts` (and `allowed_origins`) include the Railway hostname, read from config or env. Keep loopback in the list for local runs. Don't just pass `host="0.0.0.0"`: the spec says servers MUST validate `Origin`, and that call would switch validation off entirely.

Deployment check: the spec now requires the `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` headers on Streamable HTTP POSTs, and the SDK rejects missing or mismatched values with 400 / `-32020`. Railway's proxy must therefore forward `Mcp-*` headers unmodified, and must not buffer `text/event-stream` responses.

### Stage 3 — Error handling

1. **Handler exceptions no longer auto-convert to `is_error=True`.** `call_tool`'s existing `try/except` already returns `build_tool_result(error_response)` on every path and survives, but every path is audited. An exception that escapes now becomes a JSON-RPC error, not a tool-level error, and the SDK strips its message: `2026-07-28` clients get `-32603 "Internal server error"`, and legacy-era clients get code `0`.
2. **`read_resource` `ValueError`s** (`server.py:631,636,641,646`) must be re-raised as `MCPError` carrying `INVALID_PARAMS` (`-32602`, from `mcp_types`), replacing the old `-32002`. A bare `ValueError` would be flattened into the generic internal error above. `handler_exception_to_error_data` is the SDK's internal mapping (it passes `MCPError` through and maps pydantic `ValidationError` to `-32602`); it is not something we call.

### Stage 4 — MCP Apps (replaces mcp-ui-server)

Wiring, per §3.6:

```python
apps = Apps()
apps.add_html_resource("ui://nvidia/search",  SEARCH_APP_HTML,  name="search-ui")
apps.add_html_resource("ui://nvidia/content", CONTENT_APP_HTML, name="content-ui")

# 1. merge apps.resources() into on_list_resources
# 2. serve their .text from on_read_resource
# 3. stamp _meta={"ui": {"resourceUri": "ui://nvidia/search"}} on the tool schema
# 4. server.extensions["io.modelcontextprotocol/ui"] = apps.settings()
```

No `ResourceCsp` is required: client-side rendering makes no outbound requests. Omitting `connect_domains` keeps the app sandboxed by default, which is the stricter and correct posture.

**Rendering inversion.** Today `ui/templates.py` and `ui/components.py` bake search results into HTML strings server-side. Under Option 2 the `ui://` resource is a static shell — markup plus the existing CSS plus JS — that reads the tool result's `structured_content` and renders in the browser.

| File | Fate |
| --- | --- |
| `ui/styles.py` (462 lines) | **Survives**; `STYLES` is inlined into the shell |
| `ui/components.py` (293) | Rendering logic ported to JS |
| `ui/templates.py` (167) | Rendering logic ported to JS |
| `ui/renderer.py` (93) | Reduced to shell assembly (HTML + `STYLES` + JS) |
| `pyproject.toml` `[ui]` extra | `mcp-ui-server` dependency removed |

New JS lives under `src/mcp_nvidia/ui/app/` as `.js` files shipped as package data, and `renderer.py` reads and inlines them into the shell at import time (alongside `STYLES`). No bundler is introduced and the published package stays a pure-Python wheel; `MANIFEST.in` and the hatch wheel config must include the new `.js` files.

### Stage 5 — Docs, packaging, release

- `pyproject.toml`: `version = "1.0.0"`, `mcp>=2.2.0,<3`, `starlette>=1.3.0`, drop `mcp-ui-server`, delete the stale `2025-06-18` comment on the `mcp` pin.
- `package.json`: `version` → `1.0.0` (kept in step via `scripts/sync-version.py`).
- `README.md` (~10 sites) and `DEPLOYMENT.md` (~10 sites): `/sse/` → `/mcp`, `"transport": "sse"` → `"transport": "http"`, refresh health-check sample output.
- `CHANGELOG.md`: breaking-change entry for 1.0.0.
- **0.9.0**, branched from `main`, pins `mcp>=1.28,<2.0.0` and is released **before** 1.0.0. It is a separate release, not part of this migration's work.

## 6. Testing

### Ported

- `tests/test_client.py` — to the v2 client API (no handshake to establish).
- `tests/test_resources.py` — handlers now take `(ctx, params)`.
- `tests/test_ui_rendering.py` — Python component/template tests are superseded by JS tests; `STYLES` assertions are retained.

### New conformance tests

Targeting precisely what a mechanical port drops silently:

- `tools/list`, `resources/list`, `resources/read` return `ttl_ms == 3_600_000` and `cache_scope == "public"` (guards the `"private"` default).
- Unknown resource URI returns `-32602`, not `-32002` and not the generic `-32603`, on both eras.
- A request with a non-loopback `Host` in the configured allow-list succeeds, and one with an unlisted `Host`/`Origin` is rejected (guards the §3.5 default).
- **Dual-era**: a `2025-11-25` client and a `2026-07-28` client both succeed against one `/mcp` app.
- `/sse` and `/sse/messages` return `410` with `moved_to`.
- Lifespan genuinely enters `session_manager`, asserted via a live request.
- `tools/list` includes the `_meta.ui.resourceUri` binding; `resources/list` includes both `ui://` resources with mime type `text/html;profile=mcp-app`.
- `server.extensions` advertises `io.modelcontextprotocol/ui`.

### New JS tests

`node --test` (built into Node 25; `package.json` has zero dependencies and stays that way), covering the shell's render functions against representative `structured_content` fixtures shared with the Python tests.

## 7. Risks

| Risk | Mitigation |
| --- | --- |
| Client-side rewrite (Stage 4) is the largest single chunk and rides along in an already-large release | It is independent of Stages 1–3; if it slips, those can ship first and Stage 4 follows before the 1.0.0 tag |
| Railway proxy may strip `Mcp-*` headers | Explicit deployment check in Stage 2 before cutting 1.0.0 |
| `starlette` 0.x → 1.x may break the `/health` and error routes | Covered by existing route tests; surfaced early since Stage 2 touches the app factory |
| Hosts' MCP Apps rendering behaviour is new and may differ in practice | Shell is deliberately dependency-free and sandboxed; no CSP grants to revoke later |

## 8. Out of scope

- Migrating to the high-level `MCPServer` API (Decision 2 / §4.1).
- Tasks extension, subscriptions, Roots, Sampling, Logging.
- OAuth / authorization hardening — this server has no auth surface, so `iss` validation, Client ID Metadata Documents, and `application_type` do not apply.
